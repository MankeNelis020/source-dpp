# SOURCE P0.1 — Security and infrastructure hardening

Milestone base: `cc303f6` on `cursor/p0-production-architecture-f5f6` (PR #4).

This is a hardening milestone. The Missing Information Engine loop is unchanged:

`InformationRequirement → ResolutionCase → ResolutionAttempt(s) → Readiness → READY | UNRESOLVED`

A supplier request remains one attempt. No new product features, unhappy flows, DPP designer, or domain rewrite.

## B. Proposed structured disclosure model

Replace boolean `visibility === "protected"` and free-text `replaceAll` as primary enforcement.

```ts
type DisclosureLevel =
  | "FULL"
  | "VALUE_ONLY"
  | "ATTESTATION_ONLY"
  | "METADATA_ONLY"
  | "EXISTENCE_ONLY"
  | "NONE";

interface DisclosureDecision {
  level: DisclosureLevel;
  canRevealIdentity: boolean;
  canRevealEvidenceId: boolean;
  canRevealFilename: boolean;
  canRevealIssuer: boolean;
  canRevealValue: boolean;
  canRevealValidity: boolean;
  canRevealOwner: boolean;
  canRevealHash: boolean;
  reason: string;
  policyVersion: "p01-v1";
}
```

**Evidence**

| Viewer entitlement | Projection |
|---|---|
| `evidence:read` + public/on-file | `EVIDENCE_RECORD` with tenant-scoped opaque ref, filename if allowed |
| private without `evidence:read_private` | `EVIDENCE_ATTESTATION` — trust-derived status + `validUntil` only |
| protected / confidential upstream | `EVIDENCE_ATTESTATION` — no canonical id, storage key, filename, owner, issuer, tenant, hash |

Opaque refs are `evr1_` AES-256-GCM tokens. The canonical evidence id is encrypted; `organisationId` is AAD so another tenant cannot decode the handle. Decode is O(1) — there is no HMAC scan of the tenant evidence list. They are not authorization. Every fetch re-evaluates policy.

**Attestation status** follows engine claim trust, not “bytes exist and are not expired”:

| Linked claim trust | Attestation `status` |
|---|---|
| expired evidence | `EXPIRED` |
| none / `DECLARED` | `ON_FILE` |
| `EVIDENCED` | `EVIDENCED` |
| `VERIFIED` or `TRACEABLE` | `VERIFIED` |

`VERIFIED` means SOURCE has a linked claim at that trust level. It does not mean “a file is on disk”.

**Actors** continue as `visible` vs `PROTECTED_UPSTREAM_SOURCE`. Identity fields are omitted unless `canRevealIdentity`.

**Audit views**

| View | Who | Contains |
|---|---|---|
| Internal security | `audit:read_internal` | `privateContext` + protected refs as opaque handles |
| Tenant | org members | Human copy from `action` + `publicContext` only |
| Supplier portal | portal grant | Portal-relevant actions for allowed cases only |

Free-text sanitization remains a **defensive fallback**, not the correctness mechanism.

UI must consume projections. React must not decide disclosure.

## C. Outbox transaction design

Production command path (`PostgresPersistence.transaction`):

```
BEGIN
SET LOCAL source.organisation_id = '<tenant>'
SELECT engine_states WHERE organisation_id = $1 FOR UPDATE
resolve processed_commands (idempotency)
load engine JSON / required aggregates
check expectedVersion → CASE_CHANGED
applyCommand (domain, in-memory)
UPDATE engine_states
INSERT processed_commands
INSERT audit_events (structured)
INSERT outbox_events (semantic_key, ON CONFLICT DO NOTHING)
COMMIT
```

On any throw: `ROLLBACK`. Partial command state is not persisted.

**Semantic keys** (not `caseId:eventType` alone):

| Side effect | Key |
|---|---|
| First supplier request | `{caseId}:REQUEST_INITIAL:v1` |
| Day-N reminder | `{caseId}:REMINDER:DAY{n}:v1` |
| Secondary contact | `{caseId}:SECONDARY_CONTACT:v1` |

A day-7 reminder is a different key from day-3. Retry of the same day-3 row does not insert a second row (`UNIQUE (organisation_id, semantic_key)`).

Worker:

1. `claimBatch` — `FOR UPDATE SKIP LOCKED` (Postgres) or in-process claim (memory)
2. Provider send with `idempotencyKey = semantic_key`
3. Success → `SUCCEEDED`; retryable fail → `FAILED` + backoff; non-retryable or max attempts → `DEAD_LETTER`
4. Dead letter opens a Needs You task: transport failure, not supplier non-response

Critical failure avoided: DB commit without queued email (outbox insert is in the same transaction). Duplicate email after worker crash is avoided by provider idempotency key + status claim.

## D. Distributed rate limiter port

```ts
interface RateLimiter {
  consume(input: { key: string; limit: number; windowSeconds: number }): Promise<{
    allowed: boolean;
    remaining: number;
    resetAt: Date;
  }>;
}
```

| Adapter | Use |
|---|---|
| `MemoryRateLimiter` | Unit tests and single-process demo |
| `PostgresRateLimiter` | Production / preview shared state (`rate_limit_windows` upsert) |

**Not** Redis in domain code. Redis remains a valid future adapter behind the same port.

Portal keys (token never logged; fingerprint = truncated SHA-256):

- `portal:token:{fingerprint}`
- `portal:ip:{ip}`
- `portal:token-ip:{fingerprint}:{ip}`
- `portal:cmd:{grantId}:{commandType}`
- `auth:login:{ip}`
- `evidence:read:{org}:{principal}`

**Trade-off:** Postgres counters add a write per consume and are coarser than Redis INCR. They are correct across Vercel instances, regions, and restarts without a new vendor in the domain. Advisory-lock alternatives were rejected as harder to reason about for windowed quotas.

## E. PostgreSQL test strategy

`MemoryPersistence` remains the fast domain/unit adapter. `PostgresPersistence` implements the same `PersistencePort`.

Engine aggregates stay JSONB in `engine_states` so SQL does not redefine domain semantics. Security-critical rows (commands, audit, outbox, grants, evidence objects, shareable trust directory) are structured tables.

Shared security assertions live in `src/server/source/security-suite.ts` and run against both adapters.

| Layer | Command |
|---|---|
| Memory (always) | `npm test` |
| Postgres (required in CI) | `npm run test:postgres` with `DATABASE_URL` |

CI starts Postgres, applies migrations as `source_migrator`, runs isolation tests as `source_app` (not superuser). If `DATABASE_URL` is missing in CI, `test:postgres` **fails** with a clear message. Locally, the job is an explicit gate (`SOURCE_REQUIRE_POSTGRES=1` or CI).

## F. Migration risks

| Risk | Mitigation |
|---|---|
| Evidence API shape changes (`id` → attestation / opaque ref) | Case detail and evidence GET already go through server projections; UI demo catalogue pages stay on demo data this milestone |
| Audit `detail` no longer the tenant source of truth | Structured fields + projection copy; keep `detail` only as generated internal fallback |
| Existing hashed portal tokens | Unchanged (`sha256` at rest); fingerprint is telemetry-only |
| Command/outbox atomicity | New behaviour for Postgres; memory uses a mutex transaction that still inserts outbox before return |
| Organisation ids are domain strings (`acme`), P0 schema used UUID | Operational tables use `TEXT` organisation ids so domain identity is unchanged |
| RLS vs JSONB snapshot | RLS on `engine_states.organisation_id`; application still filters by principal org |
| Demo session secret | Production refuses to boot without `SOURCE_SESSION_SECRET`; demo auth stays explicitly non-production |

### Rollback / forward-fix

- `0001` operational foundation is additive. Dropping it is a full reset of empty environments only.
- `0002` hardening tables (`outbox_events`, `rate_limit_windows`, audit JSON columns, RLS, roles) can be reversed by dropping those objects; do not rewrite audit `detail` back into a security control.
- Projection changes are additive (`type`, `evidenceVisible`). Clients that required `evidence.id` for protected rows were already leaking; they must use opaque refs or attestations.

### Data retention direction (placeholders, not implemented)

| Category | Direction |
|---|---|
| Audit | Long-lived, append-only; tenant vs internal views |
| Evidence | Immutable; legal deletion later, no overwrite |
| Portal grants | Hash retained after revoke/expiry for forensics; raw token never stored |
| Processed commands | Retain for idempotency window (90 days suggested) |
| Outbox | SUCCEEDED compact after 30 days; DEAD_LETTER until operator ack |
| Sessions | Expiry + revoke; do not keep forever |
| Import temp | Delete upload bytes when job completes or after 24h; jobs are tenant-scoped metadata |

## Security controls review (headers, CSRF, portal, session)

**Headers** (`next.config.ts`): `Content-Security-Policy`, `Referrer-Policy`, `X-Content-Type-Options`, `X-Frame-Options` / `frame-ancestors`, `Permissions-Policy`, `Strict-Transport-Security` (production).

**Supplier portal** (`/s/*`, `/api/portal/*`): `Referrer-Policy: no-referrer` because the bearer token is in the URL path. Residual leakage (history, screenshots, proxy logs) is accepted rather than redesigning portal auth. No additional third-party scripts on portal pages.

**CSRF:** Cookie-authenticated mutations require Origin or Referer matching `Host`. SameSite=Lax is defense in depth, not the whole design. Portal bearer endpoints are capability-URLs; Origin is still checked when present; missing Origin is allowed for non-browser callers. The secret is the token, not a cookie.

**Session:** httpOnly, Secure in production, SameSite=Lax, server-issued HMAC, 12h expiry, `sid` for revoke. Demo login is **not** production IdP. Architecture does not encode password hashing in the domain; a future OIDC adapter can issue the same session cookie.

**SQL:** Parameterized queries only. Runtime role `source_app` is not schema owner. Migrator applies DDL separately.

## G. Scale triggers (pilot keeps the simple shape)

These are documented limits, not work to do now. Do not normalize or incrementalize until profiling says the trigger fired.

### Shareable trust directory rebuild

`PostgresPersistence.saveEngine` deletes all `shareable_trust_objects` for the organisation and re-inserts every claim. That is correct and cheap at pilot size.

**Trigger:** ~100k claims per tenant, or measured save latency / lock time that hurts command throughput.

**Later change:** incremental / event-driven upserts of the rows that actually changed. Do not rebuild that path before the trigger.

### Tenant-level JSONB aggregate lock

One `engine_states` row per organisation is loaded, locked `FOR UPDATE` in a command transaction, and written back. For smaller manufacturers and the pilot that is simple and safe.

**Trigger:** profiling shows two independent commands in the same large tenant contending on that row.

**Later change:** decompose the aggregate. Do not normalize the snapshot preemptively.
